## Запуск текущей версии

Для сборки из исходников нужны **Windows, JDK 21+ и Node.js 22.12+** (с npm). Укажите JDK в `JAVA_HOME`, добавьте Node.js в `PATH`. Maven отдельно устанавливать не нужно: в проекте есть Maven Wrapper. При первом запуске нужен интернет для загрузки зависимостей.

В PowerShell, из папки, куда вы хотите скачать проект:

```powershell
git clone https://github.com/0Taiga0/java-blueprints.git
cd java-blueprints
.\start.cmd -Port 8094
```

Если проект скачан архивом, распакуйте его, откройте PowerShell в папке с `start.cmd` и выполните только последнюю команду. `start.cmd` запускает PowerShell-скрипт без изменения постоянных системных настроек. Первый запуск собирает клиент и сервер; следующие запускают готовый JAR. Для сборки после изменения исходников выполните `powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1`.

В репозитории хранятся исходники, примеры и проверки. Зависимости, локальные настройки инструментов и готовые сборки в Git не добавляются.

Откройте http://127.0.0.1:8094. Уже работающий старый сервер не обновляется автоматически. При занятом порте выберите другой.

## Визуальный редактор

1. Импортируйте свой `.java` или выберите «Примеры → Визуальное редактирование» и нажмите «Обновить схему». У учебного примера сразу выбран соответствующий JUnit-файл.
2. Дважды щёлкните по переменной, действию, условию, заголовку цикла или вызову. Поддерживаемый Java-фрагмент раскладывается на заполненные поля.
3. Для переменной укажите имя, выберите тип и начальное значение. Для действия выберите доступную переменную и операцию. Условие собирается из значений, переменных, сравнений, логики и вложенных вызовов.
4. Перетащите новый блок из палитры в подсвеченную зону. Настройте параметры и нажмите «Добавить блок». До подтверждения исходник не меняется.
5. Перетащите действия в ветви «Да / Нет» или в тело цикла. Заголовки `for`, `foreach`, `while`, `do/while` настраиваются отдельно от тела; изменение заголовка сохраняет вложенные действия.
6. Для вызова выберите метод и заполните его аргументы. Каталог содержит методы текущего класса, доступных объектов и ряд операций Math, String, консоли и коллекций.
7. После применения обновляются Java, граф и проверка компиляции. Ошибочную правку можно отменить. Во вкладках «Тесты» и «Сравнение» проверьте результат одинаковыми тестами.

Карточки стали шире, основной шрифт — 16 px. Связи проходят под прямыми углами с отдельными боковыми маршрутами для возвратов циклов. «Читать» показывает выбранный блок при масштабе 100%; «Вся схема» даёт обзор. Пути исключений выключены при открытии.

## Как это устроено

Браузер передаёт серверу структуру действия: например имя, выбранный тип и числовое значение. Сервер создаёт узлы JavaParser, меняет нужное место настоящего дерева программы, сохраняет комментарии и заново строит код и граф. Java-синтаксис не собирается пользователем в полях формы.

- `frontend/src/flow/visual/` — формы, конструктор выражений, доступные значения и API.
- `backend/src/main/java/dev/blueprints/flow/VisualEditService.java` — разбор блока в настройки и применение изменений к AST.
- `VisualScope.java` — доступные переменные, типы и методы; `VisualExpressions.java` — выражения и проверка совместимости.
- `frontend/src/flow/routing.ts`, `layout.ts`, `geometry.ts` — размеры, размещение карточек и маршруты связей.
- `examples/VisualWorkshop.java` и `VisualWorkshopTest.java` — пример для полного цикла работы.

## Границы визуальных форм

Формы покрывают обычные одиночные объявления переменных, присваивания, арифметику и сравнения, условия, типовые заголовки циклов и вызовы из каталога. Произвольные сложные выражения, создание объектов, обращения к элементам массива, неизвестные библиотечные вызовы и другие конструкции вне этого набора сохраняются и открываются через явный режим «Редактор Java». Исходник не заменяется заглушкой.

Переименование уже используемой переменной или счётчика пока отклоняется с объяснением; автоматическое переименование всех ссылок требует отдельного рефакторинга. Смена типа может потребовать связанных правок. Финальную корректность Java проверяет компилятор; формы не заменяют полную систему типов Java. Успешные тесты подтверждают проверенные сценарии, а не эквивалентность на всех входах.

## Собираем программу мышью

1. Нажмите **Импорт** и выберите Java-файл UTF-8. Схема строится автоматически; компилятор проверяет исходник.
2. Выберите метод. Перетащите **Условие**, **Цикл** или **Действие** из левой палитры на подсвеченное место. Зоны обозначают точный смысл: до/после блока, ветка «Да»/«Нет», тело цикла.
3. Внутрь созданного условия или цикла можно перетащить следующее действие. В Java появятся соответствующие фигурные скобки и вложенные операторы.
4. Двойным щелчком откройте параметры: замените условие или текст действия. Перенос готового блока меняет его место в программе вместе с вложенным содержимым.

6. Откройте **Код** снизу, чтобы увидеть результат. **Экспорт** сохраняет Java-файл. Его можно импортировать обратно.
7. Во вкладке **Тесты** загрузите соответствующий JUnit-файл и запустите проверки. Успешная компиляция ещё не означает правильный ответ программы.

Новая операция сразу записывается в код. Пустое место полотна не является местом вставки: отпустите блок над конкретной зоной. Стрелки строятся из структуры Java; произвольное соединение стрелок не создаёт допустимый оператор языка.

## Как это работает — простыми словами

Схема — это изображение настоящего дерева Java. Когда вы бросаете действие в тело цикла, сервер вставляет его именно в список команд этого цикла. Затем он печатает Java, заново читает получившийся файл и строит новую схему. Поэтому код и блоки обновляются вместе.

Перед изменением сервер проверяет версию файла и выбранное место. Нельзя перенести цикл внутрь самого себя или оставить `break` без цикла. Ошибка операции не меняет исходник. После допустимой структурной правки компилятор отдельно проверяет типы и переменные. Во время сборки программы промежуточный вариант может не компилироваться — такая ошибка видна, её можно исправить следующей правкой или отменой.

Комментарии сохраняются, но форматирование после правок нормализуется. Комментарий удалённого фрагмента может остаться свободным комментарием метода. Перемещение логики намеренно может изменить поведение; проверяйте его тестами.

## Границы редактора

Редактируется один Java-файл и выбранный метод, конструктор или инициализатор. Внутренние блоки не переносятся между методами. Начало/конец, синтетические узлы и части заголовка цикла не удаляются как самостоятельные команды. Сложная конструкция, показанная единым блоком, не превращается автоматически в набор редактируемых вложенных действий. Ошибки типов доступны через компиляцию; доказательства эквивалентности для всех входов нет.

| Удаление одинаковых веток if/else | Ветви совпадают по AST; условие входит в ограниченное безопасное подмножество выражений над примитивными параметрами | Общие действия, их область видимости и комментарии |
| Объединение вложенных if | Внешний if содержит только следующий if, у обоих нет else, нет неподдерживаемых конструкций | Порядок вычисления условий и короткое замыкание через && |

Например, `if (a) { if (b) { work(); } }` превращается в `if ((a) && (b)) { work(); }`. Условие b всё ещё вычисляется только после истинного a. Это похоже на проверку «есть билет, и билет подходит»: вторую проверку не делают, когда билета нет.

Для удаления одинаковых веток правила строже. Если условие вызывает функцию, меняет переменную, обращается к неизвестному имени, требует распаковки объекта или может вызвать неподдерживаемое исключение, автоматическое удаление недоступно. Для ветвей с локальными или анонимными классами, лямбдами и ссылками на методы удаление также недоступно: объединение могло бы изменить идентичность создаваемых объектов. Проверки в неподдерживаемых формах не обходятся даже зелёными тестами.

Большие методы, повторяющиеся последовательности действий, пустые catch и замена вложенного поиска индексом пока остаются рекомендациями для ручного решения. Универсальное автоматическое исправление могло бы изменить смысл программы.

Эти две операции **упрощают структуру кода**. Они не обещают уменьшить Big O или ускорить выполнение в определённое число раз.

### Что именно сравнивается

«До» внутри оптимизации — текущий код непосредственно перед этой правкой. Это не обязательно первоначально загруженный файл. «После» — предложенный сервером код, который ещё не применён. Обе версии компилируются и запускаются с одним точным снимком JUnit-файла в отдельных процессах.

Кнопка применения доступна только для актуального полного результата «Совпало на тестах»: обе версии прошли один и тот же непустой набор, нет пропусков или сокращённого отчёта. Ошибка исходника, ошибка кандидата, тайм-аут или отсутствие тестов не разрешают применение.

Если изменились код, имя файла, предложение или тесты, прежнее разрешение на применение больше не действует. Отмена предпросмотра ничего не меняет. После применения исходная версия «до» в прежней панели сравнения сохраняется: можно отдельно проверить весь путь от загруженного файла.

Зелёные тесты означают совпадение на проверенных примерах, а не доказательство для всех возможных входов. Поэтому сначала действуют ограничения преобразования AST, а затем — тесты.

### Как это устроено и что разобрать

1. **optimization/OptimizationService.java** — составляет список предложений, заново проверяет версию и выбранную операцию, меняет копию AST и создаёт предпросмотр.
2. **optimization/OptimizationModels.java** и **OptimizationController.java** — данные и запросы `/api/optimization/options` и `/api/optimization/preview`. Клиент передаёт идентификатор предложения, а не произвольные координаты замены.
3. **frontend/src/optimization/** — выбор предложения, просмотр полного diff в OptimizationDiff.tsx, снимок проверки и запрет применения устаревших результатов.
4. **App.tsx** — общий набор тестов, применение одной записью истории, обновление графа и отмена.
5. **check/CheckService.java** и **BehaviorComparison.java** — прежний механизм двух запусков с одинаковыми тестами; оптимизация использует его повторно.
6. **roundtrip/OptimizationIntegrationTest.java** — реальные запросы API, отказ для опасных условий и сравнение исходного/преобразованного примера.
7. **examples/OptimizationExamples.java** и **OptimizationExamplesTest.java** — учебные случаи с результатами, побочными эффектами, исключениями и коротким замыканием.

Новые зависимости не требуются: JavaParser преобразует AST, Monaco показывает diff, React управляет состоянием, JUnit проверяет ответы программы.

### Что проверяется

| Проверка | Когда появляется | Что предлагает |
| --- | --- | --- |
| Большой метод | Больше 40 непустых операторов; фигурные скобки не считаются отдельным действием | Выделить самостоятельные задачи в методы |
| Глубокая вложенность | Четыре и более вложенных уровня условий, циклов и других конструкций управления | Упростить структуру, проверить возможность раннего выхода |

| Одинаковые ветки | AST ветвей if/else совпадает без учёта комментариев | Проверить намерение; условие нельзя удалять вслепую, оно может иметь побочные эффекты |
| Повтор трёх действий | Три последовательных действия повторяются в одном методе | Рассмотреть выделение общего метода |
| Вложенные обходы | Распознаны перемножающиеся обходы данных | Проверить необходимость повторного поиска, возможную пользу индекса или множества |
| Неясная граница цикла | Анализатор не распознал число повторений | Разобраться в условии и шаге; это не утверждение о бесконечном цикле |

Каждое замечание содержит причину, рекомендацию, строку и связи с узлами. Если один finally показан несколькими маршрутами, связанные копии получают индикаторы. При переходе к скрытому обработчику включается показ исключений.

### Big O простыми словами

Представьте список покупок из n товаров. Посмотреть каждый товар один раз — O(n). Пройти список два раза подряд — тоже O(n): работы стало вдвое больше, но она растёт так же, как список. Сравнить каждый товар с каждым — O(n²): при удвоении списка сравнений становится примерно вчетверо больше. Каждый раз отбрасывать половину вариантов — O(log n).

Панель отдельно показывает **«По обходам»** и **«Метод целиком»**. Число проходов может быть понятно, а стоимость вызванной функции — нет. Например, цикл вызывает сортировку или пользовательский метод. Тогда первая оценка может быть O(n), а вторая — **«Не определено»** с причиной. Это честнее, чем считать неизвестный вызов бесплатным.

Это **условная верхняя граница** для распознанных конструкций, а не доказанная точная формула. Последовательные участки складываются, вложенные перемножаются, постоянные множители отбрасываются. Разные размеры обозначаются n, m и следующими буквами; их смысл перечислен рядом. Фиксированное число повторений считается O(1). Для обычного while, зависимых или изменяемых границ и нераспознанного шага оценка может отсутствовать. Условия оценки раскрываются прямо в панели.

Секунды запуска JUnit не используются для Big O. Панель не обещает ускорение «в 2,5 раза», не исправляет программу сама и не заменяет компиляцию или тесты. Стоимость библиотек, рекурсии, динамических типов и операций с объектами в общем случае не выводится. Поддержка Java в графе шире, чем набор распознаваемых анализатором алгоритмов.

### Как это устроено и что разобрать команде

1. **AnalysisModels.java** — форма отчёта: замечания, оценки методов, ограничения; простой контракт между Java и React.
2. **AnalysisAst.java** — обход дерева JavaParser. Вложенная лямбда или отдельный класс не прибавляются к работе внешнего метода.
3. **SourceAnalyzer.java** — правила «найди подозрительное место», рекомендации и привязка к уже построенным блокам схемы. Исходный AST не изменяется.
4. **ComplexityEstimator.java** — сложение последовательных участков, умножение вложенных обходов и причины «не определено». Начните с cost, forFactor и классов Cost/Term.
5. **RoundTripService.java** — из одного AST получает схему и анализ; поэтому строки и блоки относятся к одной версии исходника.
6. **frontend/src/analysis/AnalysisPanel.tsx** — карточки проблем, фильтр, оценки и кнопки переходов.
7. **App.tsx → navigateAnalysis** и **flow/MethodDiagram.tsx** — выбор метода, выделение строки, центрирование графа и отметки на блоках.
8. **SourceAnalyzerTest.java** и **roundtrip/AnalysisIntegrationTest.java** — примеры, на которых проверяется корректность оценок, ссылок и обновления после правок.

Новые библиотеки не потребовались: JavaParser читает структуру кода, собственные правила анализируют её, React рисует панель, React Flow выделяет блоки, Monaco — строки. Анализ ограничен по числу узлов, глубине и количеству замечаний; неполный отчёт помечается явно.

## Этап 7: сравнение поведения до и после

Ниже редактора тестов появился раздел **«Сохранилось ли поведение?»**. Он проверяет сохранённую версию «до» и текущую версию «после» одним и тем же JUnit-файлом.

### Быстрый эксперимент

1. Запустите новую сборку: в PowerShell выполните `& ".\start.cmd" -Port 8086` из папки проекта, затем откройте http://127.0.0.1:8086. Если старая сборка уже работает на другом порту, она может продолжать работать.
2. Нажмите «Открыть пример», выберите «Тесты PriceCalculator».
3. Нажмите «Сравнить до и после». Оба запуска должны пройти 4 теста, отчёт — «Совпало на тестах».
4. Постройте схему кнопкой «Преобразовать код», выберите действие `sum += price;`, нажмите «Изменить блок» и замените его на `sum += price * 2;`.
5. Повторите сравнение. До изменений проходят 4 теста, после — 2; ещё 2 показывают ошибки: ожидалось 400, получилось 800; ожидалось 10, получилось 20.
6. Нажмите «Отменить» в панели схемы и сравните снова: обе версии опять должны пройти 4 теста.

Тесты задают одинаковые вопросы обеим версиям программы. Если старая программа отвечает правильно, а новая ошибается, таблица отмечает **«Новая ошибка»**. Это называется регрессией.

### Что означает отчёт

| Результат | Значение |
| --- | --- |
| Совпало на тестах | Обе версии прошли все обнаруженные тесты; наборы совпали, пропусков и сокращённого отчёта нет |
| Найдены расхождения | Ранее успешный тест стал ошибочным или в новой версии появилась ошибка запуска тестового набора |
| Ошибка уже была в исходнике | Старая версия не компилируется или не проходит тесты; две одинаковые ошибки не означают успешную проверку |
| Сравнение не завершено | Есть тайм-аут, ошибка компиляции новой версии, нет тестов, пропуски, разные наборы, неоднозначные имена или неполный отчёт |

В строках также видны «Исправлено», «Ошибка в обеих версиях», «Пропуск» и «Нет пары». Диагностика компилятора и полный доступный вывод открываются отдельно для каждой версии. Длительность включает компиляцию и JUnit, поэтому её нельзя считать ускорением самого алгоритма.

После изменения кода, тестов, имени файла тестов или версии «до» результат становится **устаревшим**. Перепроверка запускается кнопкой; редактирование не запускает Java автоматически.

### Как сохраняется версия «до»

- Загрузка Java-файла или встроенного примера сохраняет его текст отдельно в `baselineSource`.
- Правки схемы, ручное редактирование и отмена/повтор не переписывают этот снимок.
- «Посмотреть код „до“» раскрывает сохранённый текст.
- «Сделать текущий код версией „до“» позволяет осознанно начать новый этап сравнения. «Вернуть загруженную версию „до“» восстанавливает исходную точку сравнения.
- Исходник для кнопки отката редактора хранится отдельно в `initialSource`; смена точки сравнения не меняет его.
- Снимки живут в памяти вкладки до перезагрузки. Новый файл или пример задаёт новую исходную версию.
- «Скачать отчёт» сохраняет JSON: обе проверенные версии, один текст тестов, время проверки и результаты. Даже у устаревшего отчёта скачивается проверенный снимок, а не новый текст редактора. Импорта этого JSON пока нет.

### Как это работает внутри

1. `ComparisonPanel.tsx` берёт неизменяемый снимок двух версий и одного набора тестов.
2. `POST /api/check/compare` принимает `fileName`, `baselineSource`, `source`, `testFileName` и `testSource`.
3. `CheckService.compare` проверяет входные данные и занимает один общий слот выполнения на всю пару. Другой запуск в это время получает понятный ответ «Уже выполняется проверка».
4. Первая версия компилируется с тестами и запускается в отдельной JVM. Для второй создаются другая временная папка и новая JVM, с тем же текстом тестов. Статические переменные и относительные файлы первого запуска не переходят во второй.
5. Ошибка компиляции, тестов или тайм-аут первой версии не отменяет проверку второй. У каждой версии свой лимит: 15 секунд на компиляцию и 8 на тесты; браузер ждёт пару до 65 секунд.
6. `JunitReportReader` читает ограниченный XML-отчёт. `BehaviorComparison` сопоставляет тесты по классу и имени, а не по их порядку, длительности или служебному выводу JUnit. Повторяющиеся имена не сопоставляются наугад.
7. Сервер возвращает два результата и строки сравнения. Браузер подсвечивает изменения и сохраняет снимок для проверки актуальности.

### Какие файлы разобрать команде

1. `frontend/src/App.tsx`: разница между `source`, `initialSource` и `baselineSource`.
2. `frontend/src/check/ComparisonPanel.tsx`: запуск, снимок отчёта, проверка актуальности, таблица, скачивание JSON.
3. `frontend/src/check/api.ts`: один запрос с двумя версиями и общими тестами.
4. `backend/src/main/java/dev/blueprints/check/CheckService.java`: методы `compare`, `prepare`, `execute`; почему нужно два независимых запуска.
5. `backend/src/main/java/dev/blueprints/check/BehaviorComparison.java`: правила «прошёл → упал», «упал → прошёл» и защита от ложного зелёного результата.
6. `backend/src/test/java/dev/blueprints/check/ComparisonServiceTest.java`: настоящие компиляции и тесты, включая изменение блока, тайм-аут и отдельное состояние JVM.

### Границы сравнения

Проверяется то, что утверждают тесты: например, точный ответ метода через `assertEquals` или тип исключения через `assertThrows`. Два успешных, но слишком слабых теста не докажут равенство всех ответов программы. Вывод System.out/System.err автоматически не сравнивается с выводом другого запуска: для него нужно добавить проверку в тест. Служебный вывод JUnit содержит время и другие меняющиеся данные, поэтому сравнение его как обычного текста давало бы ложные различия.

Для воспроизводимости используйте фиксированные входные данные, независимые тесты и управляемые источники времени/случайности. Набор без тестов, с пропусками или сокращённым отчётом не получает общий зелёный статус. Проверки ограничены одним исходным Java-файлом и одним JUnit-файлом; внешние зависимости не добавлены.

## Этап 6: конструкции Java в графе

У программы теперь две связанные карты:

- **Структура файла** — какие классы, интерфейсы, поля, методы и конструкторы есть в файле; кто кого содержит, расширяет или реализует. У методов виден throws.
- **Блок-схема** — в каком порядке выполняются операторы выбранного метода, конструктора или инициализатора.

На вкладке «Структура файла» сначала виден обзор классов. Выберите класс слева: откроется граф его полей и методов. Выбор детали в левом списке приближает её на схеме; «← Все классы» возвращает обзор. Нажмите на метод, затем «Открыть логику →» справа. Флажок «Внешние типы и импорты» показывает зависимости от стандартной библиотеки. В обеих картах выбор блока раскрывает полный Java-текст справа и выделяет соответствующий участок исходника. Длинная подпись самой фигуры сокращается, исходный текст не теряется.

### Покрытие требований

| Требование | Как отображается |
| --- | --- |

### Как читать исключительные пути

Сплошная линия — обычный переход. Красный пунктир — **возможное** исключение. Граф консервативный: у вызова или выражения может быть показан путь, который при конкретных значениях не сработает. Проверки catch идут по порядку: «Подходит» ведёт в тело обработчика, «Не подходит» — к следующему. Исключение, возникшее уже внутри catch, не обрабатывается соседними catch того же try.

Один finally иногда нарисован несколько раз — для выхода с результатом, исключением, break или continue. Это разные маршруты через **один участок исходника**, а не несколько копий кода. Правка действия в таком finally меняет исходный участок и заново строит все маршруты. return/throw внутри finally могут заменить прежнюю причину выхода.

В try с ресурсами сначала закрываются ресурсы, затем выбирается catch, затем выполняется finally. При уже возникшем исключении ошибка close добавляется как suppressed. Если close ломается при обычном выходе или return, исключение заменяет этот выход.

Флажок «Показывать переходы по исключениям» можно отключить, чтобы изучить обычный маршрут. При этом обработчики и пути исключений скрываются; это фильтр картинки, а не изменение программы.

Правила переходов сверены с [JLS 21, операторы switch и try](https://docs.oracle.com/javase/specs/jls/se21/html/jls-14.html) и [switch-выражениями](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.28).

### Какие части кода разобрать

1. **StructureGraphBuilder.java** — собирает карту объявлений и связей. Стрелка «содержит» не означает порядок выполнения.
2. **FlowGraphBuilder.java** — строит маршруты выполнения; Context хранит, куда ведут return, break, continue, yield и исключение.
3. **tryFlow / resources** — создают правильные пути через finally и закрытие ресурсов.

6. **MethodDiagram.tsx** — показывает обе карты, фильтры, полный текст выбранного блока и переход к коду.

Образы для разбора: AST — список деталей конструктора; граф — карта проходов между комнатами. Объявление класса описывает, из чего дом состоит. Метод описывает, куда идти при выполнении команды.

## Этап 5: добавление блоков

Интерфейс повторяет компоновку концепта: тёмная рабочая область, палитра слева, схема в центре, настройки справа, Java-код снизу. Панель компиляции и настоящих JUnit-тестов — ниже редактора. В приложении открыт один Java-файл, а список над схемой выбирает метод или конструктор.

### Первый эксперимент — добавить действие

1. Нажмите «Открыть пример», затем «Преобразовать код».
2. Выберите метод total(List<Integer>).
3. Нажмите на действие sum += price;.
4. Нажмите «Действие» слева. Можно перетащить его из палитры прямо на выбранный блок схемы.
5. Справа выберите «После выбранного блока» и оставьте sum += 1;.
6. Нажмите «Добавить в программу».
7. На схеме появится новый шаг, а в Java-коде — новый оператор сразу после sum += price; внутри if.
8. Нажмите «К тестам ↓», затем «Запустить тесты». Сумма 120 + 80 + 200 теперь равна 403; старое ожидание 400 обнаружит изменение. Проверка смешанного списка ожидает 10, получит 11.
9. «Отменить» вернёт прежнюю программу, «Повторить» снова применит вставку.
10. «Экспорт Java» сохранит текущий восстановленный код.

Введённый текст — настоящий Java. Например, sum += 1; сработает там, где существует переменная sum. Если её нет, компилятор объяснит ошибку. Палитра даёт заготовку, которую можно изменить до добавления.

### Как собрать условие или цикл

- Чтобы добавить условие, выберите место, нажмите «Условие», введите, например, if (sum > 100) {}.
- После добавления нажмите на новый ромб. Выберите «Действие», а в списке места — «Да — в начало ветки» или «Нет — в начало ветки».
- Ветки допускают новые действия, вложенные условия и циклы. Отсутствующая ветка else создаётся автоматически.
- Для цикла выберите «Цикл» и, например, for (int i = 0; i < 3; i++) {}. Затем выберите его ромб и добавьте действие «В начало тела цикла».
- «После цикла» выполняется, когда цикл закончился. «В конец тела цикла» выполняется на каждом проходе.
- «После обеих веток» выполняется после if/else независимо от выбранной ветки. Добавление после действия внутри ветки остаётся в этой ветке.
- return, break и continue завершают текущий маршрут. Нельзя поставить обычное действие сразу после них; такие позиции скрыты. Вставка, которая делает следующие операторы явно недостижимыми, отклоняется целиком.
- Если метод пустой, выберите «Начало» или «Конец». Без выбранного блока палитра предлагает начало метода.
- Если выбран оператор из заголовка for, выберите ромб цикла: заголовок не является списком обычных команд.

Нажатие на блок подсвечивает соответствующий код. «Перейти к коду ↓» прокручивает страницу к редактору. Во время заполнения формы выбор другого блока заблокирован; сначала примените вставку или нажмите крестик. Правки и история хранятся в памяти страницы: перед её закрытием экспортируйте Java.

### Как это работает простыми словами

Схема — это карта программы. Палитра — коробка с новыми деталями.

Когда вы выбираете «добавить действие в ветку Да», браузер сообщает серверу: какой метод, какой блок, какая ветка и какой текст. Сервер находит настоящую деталь в AST, вставляет рядом новую, а при необходимости добавляет фигурные скобки. Затем JavaParser печатает всё дерево обратно в Java. Из нового кода строится новая карта, поэтому стрелки и номера строк соответствуют обновлённой программе.

Сервер проверяет, что клиент работает с актуальной версией, разбирает новый оператор, сохраняет комментарии и проверяет, что напечатанный текст воспроизводит изменённое дерево. Это проверка корректности преобразования, а не обещание прежнего поведения: новый шаг может изменить ответ. Для этого нужны компиляция и ваши тесты.

### Что разобрать команде

1. frontend/src/flow/BlockPalette.tsx — заготовки блоков и форма с местом вставки. Здесь удобно добавлять свои примеры.
2. frontend/src/flow/MethodDiagram.tsx — выбор блока, перетаскивание и связь палитры со схемой.
3. frontend/src/App.tsx — применение ответа сервера, синхронизация Java и история отмены/повтора.
4. backend/src/main/java/dev/blueprints/flow/InsertableCode.java — какие места есть у действия, условия, цикла и тела метода.
5. backend/src/main/java/dev/blueprints/flow/BlockInsertService.java — основной алгоритм вставки в AST, печать и проверка комментариев.
6. BlockInsertServiceTest.java — примеры вставки в ветки, циклы и конструкторы; настоящий запуск JUnit после добавления действия.

POST /api/flow/insert принимает fileName, source, revision, methodId, nodeId, position, kind, code. Диапазоны строк сервер вычисляет сам. Ответ содержит source, conversion, selectedMethodId и selectedNodeId. Ограничение нового фрагмента — 20 КБ; каждый запрос вставляет один оператор Java (условие/цикл могут содержать вложенные операторы). Произвольные линии между фигурами не меняют программу: её структуру задают перечисленные места вставки.

## Этап 3: изменение Java через схему

1. Преобразуйте встроенный пример.
2. Нажмите на ромб price > 0, затем на «Изменить блок» справа. Можно также дважды нажать на блок.
3. Введите price >= 100 и нажмите «Применить в Java» (или Ctrl+Enter внутри формы).
4. Внизу появится новый код, в центре — обновлённая схема. Номера строк рассчитаны заново.
5. Выберите действие sum += price; и замените его на sum += price * 2;.
6. Во вкладке «Код из AST» скачайте изменённый Java-файл.
7. «Отменить» и «Повторить» в верхней панели перемещают по истории до 20 правок схемы. Ручная правка исходника, открытие файла/примера или новое преобразование сбрасывают историю.
8. Попробуйте ошибку sum += ;: форма покажет ошибку, а старые исходник и схема останутся.
9. «Отмена» или Escape закрывают форму без применения.

Условие вводится как выражение, например price > 10, без if. Действие вводится целиком с ;.
У for можно изменить один блок инициализации и один блок обновления, без ;. У for-each меняется выражение коллекции; тип и имя переменной остаются.
return и throw редактируются целиком с соответствующим ключевым словом.
Текст блоков начала, конца, break/continue, обзора и отсутствующего условия for(;;) не редактируется старой формой. Поддерживаемые блоки могут служить местами вставки новых операторов.
Для добавления блоков используйте палитру этапа 5. Удаление и произвольное переподключение стрелок пока не реализованы.

## Как правка превращается в Java

Представьте дерево AST как конструктор. Мы находим одну деталь, проверяем новую деталь и заменяем её.
Подпись блока сокращена для экрана; форма получает полный текст узла из исходных токенов.

POST /api/flow/edit получает fileName, source, revision, methodId, nodeId, replacement.
revision — SHA-256 исходника, из которого построили схему. При несовпадении сервер отвечает 409 и просит построить схему заново.
Сервер сам восстанавливает блоки и находит целевой узел. Координаты и тип узла от клиента не принимает.
Новый фрагмент разбирается JavaParser отдельно; действие должно остаться одним действием, return — return и т. д.
Затем Node.replace меняет узел AST, DefaultPrettyPrinter печатает файл, JavaParser повторно проверяет результат.
Отдельно проверяется сохранение комментариев: считаются типы и тексты, включая повторяющиеся комментарии; для Javadoc сравнивается текст после разбора оформления.
Если комментарий изнутри заменённого узла больше не привязан к нему, он сохраняется свободным комментарием окружающего блока. Его место может измениться.
Если восстановление нарушило структуру или потеряло комментарий, правка отклоняется. Исходник на сервере не хранится и на диск не записывается.

Ответ содержит новый source, conversion с новой схемой и выбранные идентификаторы.
Браузер заменяет код и схему одновременно и сохраняет предыдущую пару для отмены.
После печати файл разбирается заново: координаты старых узлов AST после изменения не используются.

Важное ограничение: проверяется синтаксис, а не соответствие типов и поведение. Например, неизвестное имя переменной или числовое выражение вместо boolean может пройти разбор, но не компиляцию.
Зелёная проверка структуры сравнивает уже изменённый код с его повторной сборкой. Она не обещает, что результат программы остался прежним.
Форматирование всего файла может измениться.

## Как устроена схема — простыми словами

JavaParser выдаёт дерево деталей программы. FlowGraphBuilder читает тело каждого метода и составляет карту: блоки и стрелки.
У каждого блока хранится адрес в исходнике: начало и конец, строка и столбец. Эти координаты берутся из исходного AST, до форматирования.

Сервер передаёт браузеру список methods. В каждой записи есть id, класс-владелец, сигнатура, режим, предупреждения, nodes и edges.
У перегрузок разные сигнатуры, а id включает позицию объявления — даже методы на одной строке различаются.

Dagre раскладывает блоки по экрану. React Flow рисует блоки и стрелки, даёт масштабирование, перемещение и выбор.
Щелчок вызывает goToRange в App.tsx: Monaco прокручивает исходник, выделяет диапазон и подсвечивает строку.
Можно также выбрать блок клавишей Tab и нажать Enter.

Схема строится на уровне операторов:
- if/else — условие с ветками Да/Нет;
- while и for — условие, тело и обратная стрелка;
- for-each — есть следующий элемент / конец перебора;
- do/while — сначала тело, затем проверка;
- return — переход к концу метода, без перехода к следующему оператору;
- throw — переход к обработчику или выходу по исключению через необходимые finally;
- break — выход из ближайшего цикла или switch;
- continue — следующая итерация (для for сначала выполняется обновление счётчика).

Вызовы других методов — отдельные действия. Схема не заходит внутрь вызываемого метода или лямбды. Обычные выражения сохраняются целиком. Вложенные switch раскрываются с учётом вычисления аргументов слева направо, короткого замыкания &&/|| и ветвления ?:.
Исключительные пути консервативны. Граф не вычисляет значения, не доказывает выполнимость условий и не разрешает типы исключений: компиляция и тесты остаются отдельными проверками.

### Первый эксперимент: как поймать изменение поведения

1. Откройте встроенный PriceCalculator.java и нажмите «Преобразовать код».

3. Нажмите «Компилировать»: javac проверит исходник, не выполняя его. Эта кнопка не компилирует тестовый файл.
4. Нажмите «Запустить тесты»: исходник и тесты компилируются вместе, затем JUnit выполняет проверки. Все четыре теста исходного примера должны пройти.
5. На схеме измените price > 0 на price >= 100. Старый отчёт будет помечен как устаревший.

7. Отмените правку и повторите запуск: снова четыре успешных теста.

Тесты не переписывают свои ожидания автоматически после правки схемы. Именно это помогает поймать случайное изменение поведения. Если новое поведение задумано вами, обсудите требования и измените ожидания осознанно.

### Как написать свои тесты

Для своего класса поменяйте имя тестового файла, имя тестового класса и вызовы методов. Можно загрузить один .java-файл тестов до 128 КБ в UTF-8. Поле тестов допускает несколько тестовых методов, @Nested и параметризованные тесты JUnit Jupiter. Если используется package, он должен совпадать с нужным пакетом в исходнике (или импортируйте публичный класс). Имя публичного класса должно совпадать с именем его файла.

~~~java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class CalculatorTest {
    @Test
    void doublesThree() {
        assertEquals(6, Calculator.twice(3));
    }
}
~~~

Первый аргумент assertEquals — какой ответ мы ждём; второй — что вернула программа. Для методов объекта сначала создайте объект. В примере методы static, поэтому объект не нужен.

«Скачать тесты» сохраняет текст тестового файла. Изменения программы скачиваются отдельно на вкладке «Код из AST» после преобразования. Содержимое редакторов и отчёт хранятся в памяти страницы, поэтому перед перезагрузкой скачайте нужные файлы.

### Что означают результаты

- Компиляция успешна: Java-код превратился в .class, но это не доказывает правильность ответов.
- Ошибка компиляции: неверные типы, неизвестные переменные, синтаксическая ошибка или недостающий класс. Нажмите на номер строки исходника или тестов.
- Тесты прошли: выполненные проверки совпали с ожиданиями. Это не доказательство правильности на всех возможных входах.
- Тесты нашли проблему: раскройте тест, сравните expected (ожидали) и actual / but was (получили). Ошибки @BeforeAll тоже считаются неуспешным запуском.
- Нет выполненных тестов: не найдены @Test или все тесты отключены через @Disabled. Пустой набор не показывается зелёным.
- Время тестов истекло: процесс остановлен. Проверьте бесконечный цикл или слишком долгий тест.
- Код или тесты изменились: старый отчёт относится к прежнему снимку. Нажмите запуск снова; переходы по старым номерам строк отключены.

### Устройство запуска

POST /api/check/compile получает fileName и source. POST /api/check/tests дополнительно получает testFileName и testSource. Оба запроса передают JSON и заголовок X-Blueprints-Local: 1. Проверки компилятора и неуспешные тесты возвращаются как обычный отчёт HTTP 200; некорректный запрос, занятый исполнитель или отсутствие JDK — как ошибка API.

1. CheckPanel отправляет текущий исходник из редактора Java. Наличие построенной схемы для компиляции не требуется.
2. CheckService создаёт новую временную папку для каждого запуска и записывает source/Имя.java, tests/ИмяTest.java.
3. Отдельный javac компилирует код с --release 21, -encoding UTF-8, -proc:none. Аннотационные процессоры отключены. Классы сервера не передаются в classpath.
4. При успешной компиляции отдельная JVM запускает официальный JUnit Console. Он включён в общий JAR проекта, поэтому во время проверки ничего не скачивается.
5. JunitReportReader читает XML-отчёт: имя теста, статус, текст ошибки. Ограничен размер отчёта, внешние XML-сущности запрещены. В интерфейс не передаются свойства JVM из XML.
6. Временные файлы удаляются после проверки; если ОС удерживает файл после остановки, папка может остаться в системном temp.

Для сборки JUnit скачивается Maven-плагином generate-resources в target/classes/runner/junit-console.jar и попадает внутрь итогового JAR. Запуск на другом компьютере требует полного JDK 21+; Node.js и Maven нужны только для пересборки.

### Ограничения исполнения

Это локальный инструмент для доверенного кода команды, не защищённая песочница для чужих программ. Отдельная JVM защищает сервер от обычного System.exit и зависшего теста, но код всё ещё может обращаться к файлам и сети с правами пользователя. Для публичного сервиса нужен отдельный контейнер/виртуальная машина с запретами сети, ограничениями файловой системы и системных ресурсов.

- Сервер слушает 127.0.0.1. Выполняющие API дополнительно проверяют loopback, Host, Origin и специальный заголовок. Разрешён локальный Vite на порту 5173.
- Одновременно выполняется одна проверка; второй запрос получает 429.
- Компиляция ограничена 15 секундами, выполнение JUnit — 8 секундами, плюс небольшое время остановки процессов.
- Heap javac ограничен 192 МБ; heap JVM тестов — 128 МБ, metaspace — 96 МБ. Это не общий лимит памяти всей ОС.
- Вывод процесса ограничен 64 КБ; детали одного теста — 4000 символами; список — 200 результатами. Большие отчёты сокращаются либо отклоняются.
- Переменные окружения сервера не наследуются, за исключением минимальных настроек Windows/временной папки. Дочерние процессы отслеживаются и останавливаются по мере обнаружения; это не гарантия против намеренного обхода.
- Нет интерактивного stdin: чтение получает конец потока. main запускается только если его вызвал тест.
- Поддерживаются один исходный Java-файл и один файл JUnit-тестов без внешних библиотек пользователя. Сравнение двух версий отдельными запусками доступно через «Сравнить до и после». Сложные многофайловые проекты пока не реализованы.

## Ограничения этапа

- Можно менять содержимое и добавлять поддерживаемые блоки в структурные места программы. Перемещение меняет только расположение. Удаление, произвольная перетяжка связей и оптимизация пока не реализованы. Запуск реализован через JUnit-тесты.
- При превышении 350 операторов, 100 уровней вложенности или 1800 узлов после раскрытия finally метод показывается одним обзорным блоком с объяснением. Это защита от слишком большого графа, а не полная визуализация такого метода.
- Методы без тела видны в структуре и списке с пояснением. Static- и обычные инициализаторы отображаются отдельно. Компактные конструкторы record пока не раскрываются отдельно; используйте обычный конструктор.
- Граф не является интерпретатором или полной моделью JVM. Обычные выражения и лямбды атомарны, внутренности библиотек не раскрываются. Семантическое разрешение имён/типов и проверка обязательного catch/throws выполняются только javac.
- Граф метода показывает вызов конструктора как действие, а поля/инициализаторы — в структуре и отдельных схемах. Полную последовательность инициализации всей иерархии классов он не разворачивает.
- Успешный разбор проверяет синтаксис. Он не доказывает, что код компилируется, разрешает все имена или работает правильно.
- Равенство деревьев без учёта комментариев — проверка структуры средствами JavaParser, а не доказательство равенства поведения.
- Принтер меняет форматирование. При редактировании и вставке отдельно проверяется сохранение количества комментариев каждого вида/содержания; точные пробелы и положение комментариев не гарантируются.
- Для компиляции доступны стандартная библиотека Java 21 и JUnit 5. Внешние зависимости пользовательского проекта пока не подключаются.
- По умолчанию приложение доступно только с этого компьютера.
- Редактор включён в сборку; во время работы ему не нужен CDN.
